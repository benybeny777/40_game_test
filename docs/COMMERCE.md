# 販売・ストア・Steamマーケット

更新：2026-10-29。実決済・Steamworks契約・ストア公開・アイテム取引は行っていない。

## 現在の実装

**現在はクライアント内の実装で、オンライン権威サーバーは未実装。** HTTP API、アカウント認証、サーバーDB、サーバー側戦闘、所有権同期、取引台帳の運用はまだ存在しない。mainプロセスはrendererより権限を持つが、利用者のPC上で動くため、販売・取引の最終的な信用源にはできない。レシート検証器とローカル排他制御のテスト成功を、サーバー実装済み・オンライン取引可能の証拠にはしない。

本体を買い切り、追加の有料商品を外観に限定する方針。キャラ・装備の強さ、経験値、小判、ドロップ率は購入で変えない。新しいダンジョンの販売方法は未決定で、今回の地面テーマ購入へ混ぜない。

地面テーマ4種（桜色・月明かり・提灯色・深淵色）のカタログ、所有権、外観選択、永続化、未確定取引の記録、決済アダプター境界を実装した。通常ビルドは販売前を表示して購入を拒否する。表示価格はSteamから取得した値だけで、未取得時はnull。本体980円・各テーマ200円などは検討用の仮値で、販売価格として確定・登録していない。

開発用のsandboxは `profile=dev`、`packaged=false`、明示的なsandbox指定がすべて揃った場合だけ有効。実決済は発生せず、所有権は製品へ移行しない。配布版で環境変数をdevへ変更してもsandboxは使えない。保存先は呼び出し側から渡す `paths.commerce` を正本にし、開発検証用のデータを利用者の保存先へ書かない。

## 接続契約

- `CommerceService({ path, profile, sandbox, packaged, appId?, steamId?, provider? })`
- `getView(): StoreView`：価格・所有・装備・販売状態・確認待ち。SteamIDや署名、鍵はrendererへ渡さない。
- `purchase(sku): Promise<CommerceResult>`：購入開始前に注文を永続化。キャンセルは確定後に再操作可能。
- `equip(sku | null)`、`getAppearance()`：所有した外観だけ有効。nullで既定の地面に戻す。
- `CommerceProvider`：mainが呼ぶ取引アダプター境界。将来は認証済みのサーバーAPIへ接続し、支払いの確定と所有権発行はサーバー側で行う。現在の`getPrice`は同期インターフェースなので、HTTP接続時には非同期の価格一覧取得／サーバー価格のキャッシュ更新と、その失敗表示を別途設計する。**サーバーと実際のSteamへの接続は未実装**。

`src/commerce/receipts.ts` は、自前の信頼する取引サーバーが発行するEd25519レシートの検証器。Steam発行のインベントリ署名を直接検証するものではない。将来の取引サーバーはSteam側の取引を確認・確定してから、AppID・SteamID・注文ID・商品ID・レシートIDを束縛して署名する。署名の秘密鍵・Steam Publisher Web API Keyはクライアントへ入れない。

未確認／通信切断／検証失敗の注文はunknownにし、自動で支払いを再送しない。同じレシートを別商品へ再使用できない。起動時のpending注文もunknownになる。保存失敗は購入を停止する。ローカルファイルだけで製品の所有権を復元せず、再確認なしの二重購入も防ぐ。**製品の所有権同期・返金／取り消し反映・unknown注文の照会と解決は、Steam接続アダプターを作る際に実装する必要がある**。現時点で実決済を有効にできる完成した課金システムとは扱わない。

## Steam側の前提

Steam上のゲーム内購入はSteam WalletのAPIを使う必要がある。購入の取引性・不正利用への対処も、ゲーム側の責任を含む。[Steam公式：ゲーム内購入](https://partner.steamgames.com/doc/features/microtransactions)

Steam Inventory ServiceはSteamアカウントのアイテムを扱う基盤で、Item Storeはその定義を使う販売の仕組み。対応したAppID、Steamworksの設定、SDK／APIアダプター、実アカウントでの受入検証が必要。[Steam公式：Inventory Service](https://partner.steamgames.com/doc/features/inventory)、[Item Store](https://partner.steamgames.com/doc/features/inventory/itemstore)

`steam/inventory-schema.json` は未公開の定義ひな型。`appid=0`は未設定を表し、そのままアップロードしない。商品ID1001〜1004はカタログと一致する。販売価格・公開アイコンURL・実AppIDを決め、Valve側で設定するまでhidden/store_hiddenを維持する。

スキーマの `marketable` はCommunity Market、`tradable`はユーザー間トレードへの適格性を示す。ここでは両方false。フラグだけを変えれば公開取引が完成するとは扱わない。[Steam公式：Inventory Schema](https://partner.steamgames.com/doc/features/inventory/schema)

## マーケットの設計境界

ローカルのセーブJSON・小判・装備袋はプレイヤー自身が変更できるため、そのままSteam取引アイテムへ変換しない。現在のストアは `market.available=false` を返し、Steamへの送信・受領・市場への出品を行わない。

マーケットを作る際は、Steam側の一意なitem instanceとサーバーの所有権台帳を照合し、認証済みアカウントと取引記録を検証する。利用者が求めるレア装備の取引には、装備を生んだ戦闘・乱数・報酬もサーバー側で検証できる必要がある。外観だけのストアを、装備マーケットの完成として扱わない。供給上限・不正発行の検出・レート制限・返金／取引保留・障害後の照合を持たせる。受け取れたか不明な送信を自動再送しない。

## 権威サーバーの最小設計（未実装）

以下は実装範囲を明確にするための設計。ローカルでサーバーとDB、専用の開発認証器、失敗試験を作ることは、Steam契約・外部公開・実課金とは別の作業として可能。

### 信用と再利用

- `src/core`の固定tick戦闘、ジョブ、装備生成、コマンド検証をサーバーでも再利用する。戦闘ロジックのコピーは作らない。`GameHost`は現在ローカル時計・ローカル保存を使うため、そのまま信用源にせず、サーバー時計・所有者別DB・単一実行権へ接続するホスト層を用意する。
- ログイン認証の結果からサーバーがアカウントを確定する。body/queryのSteamID・accountId・AppIDを信用しない。開発認証はloopback専用かつ明示的に分離し、製品モードでは受け付けない。
- サーバーがセッション開始時のseed、進行時間、入力順序、報酬とitem instanceを確定する。クライアントは操作要求のみを送り、経験値・勝利・ドロップ・任意の経過時間を確定結果として送れない。オフライン報酬もサーバーの記録時刻と上限で計算する。
- 既存のローカルセーブ／装備は`marketEligible:false`のまま。オンラインDBへのインポートや署名追加だけで取引可能に昇格させない。ローカル進行とサーバー管理進行は保存領域と画面で区別する。サーバー停止中はローカルプレイを続けられるが、その報酬を後から市場へ持ち込めない。
- レシート署名は改変検出に使えるが、返金後の所有権取り消しや最新状態の保証にはならない。実行中の`verifiedOwned`とファイル`.lock`は端末内の防御であり、複数PC・再接続・複数サーバーの競合制御にはDBの一意制約とトランザクションを使う。

### 最小API

| API | サーバーが確定する内容 |
|---|---|
| `POST /session` | 認証チケットの検証と期限付きセッション。開発用の認証器を本番へ持ち込まない |
| `GET /me` | 認証済み利用者の進行revision、装備instance、外観所有権。別利用者を指定できない |
| `POST /runs` | 保存済みの編成・装備条件を検査し、サーバーseedで探索を開始。並行runの二重報酬を防止 |
| `POST /runs/:id/commands` | 所有者、単調seq、expectedRevision、冪等キーを確認して既存coreの操作を適用 |
| `GET /runs/:id` | サーバーが進めた戦闘結果と確定報酬を返す。クライアント報酬の受領APIは作らない |
| `GET /store`・`GET /orders/:id` | 確認済み価格、所有権、pending/unknown/確定/取消。注文の再送で照会を代用しない |
| `POST /orders` | 商品・サーバー価格・認証済みアカウントに束縛して注文を登録。冪等キーの同一入力は同じ注文へ、別入力の再使用は拒否 |

出品・外部発行APIは、サーバー生まれの装備と所有権、取引保留、既存instanceとの対応が揃ってから追加する。ローカル装備JSONを受け取る発行APIは作らない。

### DBと障害時の整合性

アカウント別のversion付き進行、runと受理済みcommand seq、発行event IDが一意な装備instance、所有者・状態・revision、注文・冪等キー、検証済みreceipt ID、外観entitlementと取消状態を記録する。開発時の単一サーバーでも永続DBと再起動復旧を試験する。

報酬確定はrun更新・重複防止event・装備発行・台帳追加を同じDBトランザクションで確定する。所有者の変更や消費もrevision検査と同一トランザクションを使い、二重受領・二重売却を拒否する。取引APIには認証、入力サイズ上限、レート制限、所有者照合を掛ける。

外部決済・Steam発行はDBトランザクション内で待たず、outboxへ意図を確定してから処理する。外部の冪等性が保証されない操作は、応答不明時にunknownを保持して照合へ進み、送信をやり直さない。サーバー再起動、応答喪失、並行コマンド、別アカウントの注文照会、返金と装備中状態、DB書込失敗を受入条件とする。実Steamの照合は接続後の別受入であり、ローカルの偽provider試験と区別する。
